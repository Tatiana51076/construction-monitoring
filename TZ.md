# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (v0.2 — синхронизировано с макетом «Объектив 0.4»)

> Интеллектуальная система мониторинга строительной площадки:
> сопоставление снимков с камер с календарным графиком работ и выявление отклонений.

---

## 0. Глоссарий (единый: ТЗ ↔ макет ↔ код ↔ документация)

| Термин в ТЗ | В макете | В коде | Значение |
|-------------|----------|--------|----------|
| Этап / вид работ | Работа | `Work` | Строка календарного плана |
| Методика «этап → техника» | Справочник признаков | `rules` / `Work.required_equipment` | Какая техника/люди нужны работе |
| Зона / участок | Зона | `zone` | Территориальная привязка |
| Обнаружение техники | Наблюдение | `Observation`, `Detection` | Что видно на кадре |
| Отклонение | Замечание / расхождение | `Deviation` | Наблюдение ≠ план/отчёт |
| Отчёт подрядчика | Заявлено (в графике) | `fact_percent` | Что подрядчик проставил |
| Подтверждение | Подтверждено наблюдением | `days level 2 / days` | Доля дней, где камера видела работу |
| Событие | Кадр / смена | `snapshot`, `shift` | Единица съёмки |
| Ответственный | Контакт подрядчика | `contacts` | Кому адресуется замечание |

**Ось 1 — наблюдение**, **Ось 2 — отчётность**, **Ось 3 — сроки**. Эти три оси независимы.

---

## 1. Назначение

По снимкам с камер стройплощадки автоматически определять, какие работы фактически
идут, сверять с календарным планом и отчётностью подрядчика и выявлять отклонения с
понятным объяснением, доказательством (кадры) и оценкой риска срыва сроков.

**Главный принцип:** система не утверждает, что работа выполнена. Она фиксирует только
то, что **видела** (техника была/нет, двигалась/стояла). Всё непроверяемое честно
помечается «не проверяется», а не «выполнено».

## 2. Область действия (Scope)

**MVP:**
- один/несколько объектов, 8 типов техники, ограниченный набор работ;
- снимки (серии кадров), не видео;
- план и факт (отчёт) в канонической табличной форме;
- детекция → сопоставление → отклонения → дашборд;
- объединение наблюдений нескольких камер.

**Вне MVP:** live-видео, трекинг в реальном времени, интеграция с ERP, полноценные роли.

## 3. Пользователи

| Роль | Задача |
|------|--------|
| Руководитель проекта | видеть срывы, причины, риск; реагировать, эскалировать |
| Инженер ПТО | сверять факт с планом, вести график, видеть расхождения |
| Технадзор | фиксировать исход замечаний, удержания по КС-2 |
| Прораб/диспетчер | знать, что сейчас на площадке, где дефицит техники |

## 4. Классы техники (обязательный перечень ТЗ)

`dump_truck` (самосвал), `excavator` (экскаватор), `roller` (каток),
`manipulator_crane` (кран-манипулятор), `concrete_mixer` (бетоносмеситель),
`bulldozer` (бульдозер), `truck` (грузовик), `truck_crane` (автокран).

**Люди** — вспомогательный признак (претензия на нём одном не строится).

## 5. Входные данные

1. **Снимки:** `{path, camera_id, zone, timestamp, shift}`.
2. **Камеры:** `{id, name, zone, is_primary_for_zone, status, last_frame_at, homography?}`.
3. **Работы (план/факт):** каноническая форма, см. п. 6.
4. **Отчёт подрядчика:** та же форма + `report_date, author`.
5. **Справочник признаков:** для работы — классы техники, минимум людей, порог подтверждения.
6. **Простои по акту:** `[{date, reason}]` (погода, технология).
7. **Контакты:** ответственный подрядчика на объекте + эскалация.

|------|:---:|----------|------------------------------|
| `id` | да | идентификатор | № п/п, код |
| `object_id` | да | объект | Объект, Корпус, Секция |
| `name` | да | вид работ | Вид работ, Наименование работ |

| `zone_type` | да | area / linear 
| `source`, `version` | нет | источник/версия | — |трассируемость и версионность — из какого файла/отчёта строка, какая версия графика. Чтобы несколько загрузок (план v1, отчёт №5) не перезатирали друг друга, и было видно, какая версия актуальна

## 7. Пайплайн

```
Снимки → Детекция (техника+люди) → Дедупликация между камерами
      → Уровень дня (0/1/2/null) по работе (зона+даты)
      → Подтверждение (доля дней уровня 2 ≥ порог работы)
      → Сверка трёх осей (наблюдение / отчётность / сроки)
      → Замечания + острота + прогноз срока
      → Дашборд
```

## 8. Уровни дня (базовая единица)

```
2 · работа идёт     требуемая техника в кадре, меняет положение, людей ≥ минимума
1 · только ресурсы  техника есть, но без движения, ИЛИ нет ключевого класса, ИЛИ людей мало
0 · ничего          кадры есть, требуемой техники и бригады нет
null · кадров нет   камера молчала (в расчёт не берётся)
```

## 9. Статусы работы (Ось 1 — наблюдение)

| Статус | Условие | Действие |
|--------|---------|----------|
| `in_progress` (работа идёт) | доля дней уровня 2 ≥ порога работы | ничего |
| `resources_only` (только ресурсы) | техника стоит смену / нет ключевого класса / мало людей | спросить причину простоя |
| `nothing_detected` (ничего не обнаружено) | кадры есть, ожидаемого нет | если работа закрыта — запросить подтверждение до акта |
| `insufficient` (недостаточно данных) | кадры < 60% рабочих дней этапа | проверить камеру/объём вручную, вердикта нет |
| `not_checked` (не проверяется) | нет в справочнике / нет признаков / нет камеры / нет кадров | описать признаки/камеру |
| `not_started` (не начата) | план в будущем | — |
| `manual_resolved` (решено вручную) | человек закрыл как «объяснено»/«ложное» | — |

## 10. Правила сверки (R1–R8)

- **R1 «Работа идёт»:** доля дней уровня 2 ≥ `confirm_threshold` работы. Порог **на работу**: котлован 60%, армирование 80%, монолит 70%, бетонирование — ежедневно. Выходные и дни простоя по акту из знаменателя исключаются.
- **R2 «Только ресурсы»:** техника в кадре, но `moved=false` за смену, и/или нет ключевого класса, и/или людей < минимума.
- **R3 «Ничего не обнаружено»:** кадры есть, требуемой техники/бригады нет N дней подряд (`missing_days=2`).
- **R4 «Недостаточно данных»:** покрытие < 60% рабочих дней этапа → вердикт не выставляется.
- **R5 «Лишняя техника» (`unexpected_equipment`)** ⭐: на работе видна техника, не входящая в её справочник → замечание (низкая/средняя острота).
- **R6 «Ложное завершение» (`false_completion`)** ⭐: `fact_percent = 100`, покрытие ≥ 60%, доля дней уровня 2 < 40% → high. Формулировка: «выполнение **не подтверждено** видеонаблюдением».
- **R7 «Сроки»:** начало сдвинулось относительно плана; прогноз окончания по темпу; «+N рабочих дней к плану».
- **R8 «Отставание отчётности» (не претензия):** наблюдение выше заявленного на ≥20 п.п.

### 10.1. Multi-camera dedup (обязательно) ⭐
Один объект не должен считаться за несколько:
1. **При калибровке:** детекции одного типа в пределах `dedup_distance` и окна `dedup_window_min` → один объект (гомография на план).
2. **Без калибровки (fallback):** по (зона, тип) берётся **max по камерам**, а не сумма.
3. За камерами закреплены зоны; при перекрытии — **главная камера зоны** (`is_primary_for_zone`).

## 11. Три оси в карточке замечания

```
план на сегодня   = прошедшие рабочие дни этапа / все рабочие дни этапа
заявлено          = fact_percent из графика
подтверждено      = дни уровня 2 / прошедшие рабочие дни этапа
разрыв            = заявлено − подтверждено; метка при |разрыв| ≥ 20 п.п.
```
Единицы намеренно разные: объём (%) и дни наблюдения не складываются в одну шкалу.

## 12. Острота и прогноз

- **Острота** (сортировка ленты): закрыто без подтверждения > простой > «недостаточно данных».
- **Прогноз срока:** по наблюдаемому темпу; если объём закрыт, но не подтверждён — прогноз не выставляется.

## 13. Жизненный цикл замечания

`новое → просмотрено → запрос отправлен → закрыто (исход)`

| Исход | Смысл | Что меняется |
|-------|-------|--------------|
| Подтвердилось · удержание по КС-2 | подрядчик не доказал объём | остаётся красным + метка удержания |
| Объяснено подрядчиком | фотоотчёт, работы вне обзора | синий «решено вручную», уходит из расхождений |
| Ложное срабатывание · в модель | ошибка детектора | кадры в датасет, «решено вручную» |
| Нет ответа · эскалация | 2 суток молчания | остаётся красным + метка эскалации |

## 14. Экраны (MVP)

1. **Портфель:** карточки объектов (полоска худшего наблюдения, бейдж замечаний, стадия, «+N дн», три полоски план/заявлено/подтверждено), строка сводки, сортировки/фильтры, лента расхождений, план-факт объекта (Гант).
2. **Разбор работы:** лестница подтверждения (01 ресурсы → 02 движение → 03 объём → 04 принято), «ожидалось/обнаружено», календарь и кадры смены, гипотезы причин, история версий плана.
3. **Камера:** кадр с рамками детекций + скраббер кадров, связь с графиком.
4. **Настройка:** источник плана, режим недели, простои по акту, уведомления, тип зон, камеры, ответственные, справочник признаков.

## 15. Нефункциональные требования

- Без GPU — допустимо; GPU — приветствуется.
- Отклик API < 2 с (без времени детекции).
- Docker: `Dockerfile` + `docker-compose.yml`.
- Код модульный и документированный; БД PostgreSQL (SQLite для демо).

## 16. Критерии приёмки

- Все обязательные функции ТЗ работают сквозняком на демо-данных.
- РП за ≤30 сек понимает статус портфеля.
- Каждое замечание объяснено и подтверждено кадром.
- Multi-camera: один объект = один (не N камер).
- Пороги и справочник меняются без правки кода.

## 17. Ограничения

- Модель обучена на ограниченном/синтетическом наборе; 8 классов.
- Поведение — по серии снимков; кадры 08:00–17:00, ночные смены вне MVP.
- Работы без видимых признаков (отделка, сети, гидроизоляция) — «не проверяются».
- Число людей с камеры неточно — вспомогательный признак.
- Перекрытие зоны (штабель/бытовка закрыл обзор) — пока в «ничего не обнаружено» с гипотезой.

## 18. Рекомендации по установке камер (ТЗ п.4)

- Стационарные камеры, **одна камера → одна зона**; при перекрытии — назначить главную.
- Обзор ключевых зон: котлован, пути вывоза, склад, монтаж.
- Частота: **1 кадр/час** в смену (достаточно для уровней дня и движения).
- Ночь/плохая погода: ИК-подсветка, защита от засветки; иначе смена не оценивается.
- Высота/ракурс — для различимости классов техники.
- Для точного счёта — калибровка (гомография) и привязка камеры к плану.
- Контроль «камера молчит дольше суток» → уведомление.

## 19. Что нужно от данных (анкета к эксперту)

| Что | Поле |
|-----|------|
| Объект у работы | `object_id` | у каждой строки графика указан объект (корпус, секция, площадка).
Зачем: портфель руководителя, фильтр «по объекту», сводка, карточки объектов.
Откуда: календарный график (колонка «Объект»).
Без этого: нельзя сгруппировать работы по объектам 

| Даты плана, не проценты | `plan_start, plan_end` |даты плана, не проценты
 у работы есть дата начала и окончания, а не только «% выполнения».
Зачем: расчёт «план на сегодня», переходы статусов по времени.
Откуда: график.
Без этого: нечего считать — «план на сегодня» и сроки не построить если в графике одни проценты.


| Зона у работы, камера у зоны | `zone_id, camera_ids` | работа привязана к зоне/участку, камера привязана к зоне.
Зачем: связать наблюдение с камеры с конкретной работой (ТЗ: «зона выполнения»).
Откуда: график (зона) + настройки камер.
Без этого:  система не знает, к какой работе отнести технику.


| Уровень по каждому дню | `days: {date: 0|1|2|null}` |по каждой работе на каждый день — оценка наблюдаемости:
2 — работа идёт (техника есть, двигается, людей хватает)
1 — только ресурсы (стоит / нет ключевого класса / мало людей)
0 — ничего (кадры есть, ожидаемого нет)
null — кадров нет (камера молчала)
Зачем: базовые «кирпичики» для календаря, «подтверждено N из M дней», статусов.
Откуда: вычисляет система из снимков.
Без этого: нет ни календаря активности, ни расчёта подтверждения.


| Признак движения за смену | `moved: bool` по классу |двигалась ли техника в течение смены (не просто «была в кадре»).
Зачем: отличает «работа идёт» (2) от «только ресурсы» (1) — ключевая деталь.
Откуда: CV — сравнение позиций техники между кадрами смены.
Без этого: «стоит» не отличить от «работает» 


| Статус камеры и последний кадр | `camera.status, last_frame_at` | камера онлайн / был перерыв / молчит + время последнего кадра.
Зачем: статус «недостаточно данных», «камера молчит», уведомления, честность вердикта.
Откуда: система видеонаблюдения (API/выгрузка).
Без этого: не понять, «работы нет» или «камера умерла»


| Ответственный подрядчика | `contacts` |контактное лицо подрядчика на объекте (телефон,эл.почта)+ кому эскалировать
Зачем: кнопка «Связаться», адресность замечаний.
Откуда: настройки объекта (заполняет РП/ПТО).
Без этого: замечание «висит без адресата» — реагировать некому.


| Прогноз окончания | `forecast_end` |дата окончания работы по наблюдаемому темпу (а не по плану).
Зачем: «+N дней к сроку», прогноз сроков объекта, раннее предупреждение.
Откуда: считает система по фактической динамике.
Без этого: виден только факт отставания, но не «насколько сдвинется сдача».


| Первая версия дат и журнал | `plan_v1, history[]` | какими изначально были даты и кто/когда их менял, с причиной.
Зачем: защита от «сдвига задним числом» — перенос дат не должен снимать красный статус
Откуда: версионирование графика (импорт с версиями).
Без этого: подрядчик может сдвинуть даты и «легализовать» просрочку.

| Простои по акту | `downtime[]` |Надо подумать- задокументированные простои  с датами и причиной
Зачем: эти дни исключаются из расчёта — не считаются ни за, ни против подрядчика; серый день в календаре.
Откуда: ручной ввод (РП/ПТО).
Без этого:/простои не повине подрядчика (не завершены работы предыдущим подрядчиком,снегопад ,отключение электричества)- несправедливые претензии.

| Тип зон | `zone_type` |зона /полигон или линейная (пикетаж/километры
Зачем: для линейных объектов (дороги, тоннели) своя привязка «работа ↔ камера».
Откуда: параметр объекта.
Без этого: линейные объекты (как «Перегон Парковая—Заречная» в макете) не привязать.

| Режим недели | 5/6-дневка, праздники |
