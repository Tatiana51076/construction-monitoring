# Документация — Дашборд «Объектив» (руководитель)

## 1. Назначение

Веб-интерфейс для руководителя (РП, ПТО, технадзор). Показывает портфель объектов,
план/факт по работам, отклонения с доказательством кадром, риск и методологию. Получает
снимки и детекции с бэкенда (FastAPI) и отображает вердикты.

## 2. Технологии

- React + TypeScript (SPA)
- Vite (сборка и dev-сервер с прокси)
- Tailwind CSS + lucide-react (иконки)

## 3. Структура кода

| Файл | Назначение |
|---|---|
| `src/main.tsx` | точка входа |
| `src/App.tsx` | каркас: шапка, вкладки, hash-роутинг, живые данные |
| `src/projects.ts` | демо-данные: объекты, работы, зоны, кадры |
| `src/data.ts` | 17 классов техники + разбор ответа API (bbox) |
| `src/expected_equipment.ts` / `.json` | таблица «работа → техника» + расчёт вердикта |
| `src/liveData.ts` | загрузка /photos и обновление работ |
| `src/components/` | компоненты интерфейса |
| `vite.config.ts` | прокси на API бэкенда |

### 4.3. Контракт `/photos`

```json
{
  "file": "1790..._t-concrete.jpg",
  "image_url": "/uploads/1790..._t-concrete.jpg",
  "work": "Бетонирование",
  "zone": "Секция C",
  "detections": [ { "class": "Mixer", "confidence": 0.81, "bbox": [52.57, 53.31, 105.15, 56.47] } ],
  "works_status": [ { "work": "Бетонирование", "status": "confirmed", "found": ["mixer"] } ]
}
```

`bbox = [x_центр, y_центр, ширина, высота]` в пикселях.

### 4.4. Статусы вердикта

| Статус | Показывается как |
|---|---|
| `confirmed` | Выполнено |
| `not_confirmed` | Не обнаружено |
| `review` | Переснять |
| `unsure` | Не проверяется |

## 5. Логика расчёта вердикта

Дашборд берёт вердикт от сервера (`works_status.status`). Если сервер вернул `unsure`,
дашборд считает сам из поля `detections` и таблицы ожидаемой техники:

- `confirmed` — найдена хотя бы одна техника из required с confidence ≥ 0.5;
- `not_confirmed` — детекции есть, но не та техника;
- `review` — детекций нет совсем;
- `unsure` — работа не найдена в таблице.

Сопоставление работы: из имени файла/поля `work` извлекается код `t-<slug>`
(`t-concrete`, `t-pit`, `t-rebar`) → по `work_slugs` → название работы → `workId` строки плана.

## 6. Условия и ограничения

- Точность распознавания зависит от модели (YOLO, 17 классов).
- Работает через прокси Vite; продакшен — статическая сборка (`npm run build`).
- При недоступном API переключается на демо-данные (не падает).
- Код работы определяется по `t-<slug>`; в итоговой интеграции должен приходить `task_id`.
- Работы без видимых признаков помечаются «не проверяется».

## 7. Инструкции по запуску

### 7.1. Разработка

```bash
npm install
npm run dev          # http://localhost:5173
```

Прокси на бэкенд — в `vite.config.ts` (цель `http://217.18.63.89:8000`).

### 7.2. Сборка (продакшен)

```bash
npm run build        # соберёт в dist/
npm run typecheck    # проверка типов
```

### 7.3. Тех.режим и диагностика

В дашборде: выбрать проект → вкладка «Камеры / CV» → кнопка «Тех. режим». Блок
«Живые данные · диагностика» показывает `/health`, число фото, разбивку по вердиктам и
сопоставление нарядов; кнопка «Проверить» перечитывает данные.
