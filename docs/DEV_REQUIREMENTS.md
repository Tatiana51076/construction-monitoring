# Требования для разработчика: бизнес-правила и критерии приёмки

> **Для кого:** бэкенд и фронтенд. Чтобы реализовывать не «по догадке с макета», а по
> явным правилам и проверяемым критериям.
>
> **Источники (в порядке приоритета):**
> 1. Макет «Объектив 0.4» — `docs/mockup-obektiv-0.4.html` (сборка 0.4, правка 8, 10.09.2026).
> 2. ТЗ — `TZ.md` (v0.2).
> 3. Выжимка — `docs/REQUIREMENTS.md`.
>
> **Демо-константы макета:** «сегодня» = **4 сентября 2026, 18:00**; шести объектов,
> 35 работ; режим недели — **пятидневка**; данные демонстрационные.

---

## 0. Как пользоваться

- Каждое правило имеет ID `BR-XXX` и **критерии приёмки** `КП-BR-XXX-n` (Given/When/Then).
- Правило считается выполненным, когда проходят все его критерии.
- Если код расходится с правилом — правило главнее; расхождения вынесены в §9.

## 1. Глоссарий (макет ↔ ТЗ ↔ код)

| Макет | ТЗ | Код | Значение |
|-------|----|-----|----------|
| Объект | `object_id` | `object_id` | корпус/площадка/перегон |
| Работа | Этап / вид работ | `Work` | строка календарного плана |
| Зона | `zone` | `zone` | участок/захватка/пикетаж |
| Наблюдение | Обнаружение | `Observation`, `Detection` | что видно на кадре |
| Чип наблюдения | Статус (Ось 1) | `status` | работа идёт / только ресурсы / … |
| Замечание | Отклонение | `Deviation` | наблюдение ≠ план/отчёт |
| Заявлено | Отчёт подрядчика | `fact_percent` | процент факта из графика |
| Подтверждено | Подтверждение | `level2_ratio` | доля дней ур.2 от прошедших рабочих |
| Уровень дня | Уровень дня | `DayLevel.level` | 2 / 1 / 0 / null |
| Справочник признаков | Справочник | `data/equipment_rules.json` | что и сколько ждать от работы |
| Простой по акту | `downtime[]` | `Downtime` | день ни за, ни против подрядчика |
| Прогноз | `forecast_end` | `WorkStatus.forecast_end` | дата окончания по темпу |
| Острота | — | `risk_score` (частично) | балл для сортировки ленты |

**Три оси** (в макете показаны раздельно и **никогда не смешиваются**):
**Ось 1 — наблюдение** (что видела камера), **Ось 2 — отчётность** (что заявил подрядчик),
**Ось 3 — сроки** (сдвиг/прогноз).

## 3. Бизнес-правила

### Блок A. Уровень дня (наблюдение)

**BR-101. Уровень дня принимает 4 значения.**
Источник: макет «Как считаются цифры → Уровень дня»; ТЗ §8.
- `2 · работа идёт` — техника из справочника в кадре, **меняет положение**, людей ≥ минимума;
- `1 · только ресурсы` — техника есть без движения, **или** нет ключевого класса, **или** людей мало;
- `0 · ничего` — кадры есть, ожидаемого нет;
- `null · кадров нет` — камера молчала (в расчёт не берётся).

КП-BR-101-1: Given за день есть кадры, техника в кадре стоит, людей достаточно → уровень `1`.
КП-BR-101-2: Given кадры есть, техники/бригады нет → уровень `0`.
КП-BR-101-3: Given кадров за день нет → уровень `null` и день **не входит** в знаменатель.
КП-BR-101-4: Given техника движется и не хватает ключевого класса → уровень `1`, не `2`.

**BR-102. Признак движения — за смену, по серии кадров.** Одиночный кадр не доказывает ни движения, ни простоя.
КП-BR-102-1: Given один кадр смены → движение не определяется (уровень не может быть `2` только по нему).

**BR-103. Люди — вспомогательный признак.** Претензия не строится только на числе людей.
КП-BR-103-1: Given людей 0, техника работает и движется → уровень `1` (не ресурс-вердикт «ничего»).

**BR-104. Уровень ставится всем дням, включая дни вне плана** — чтобы видеть работу раньше/позже графика.

**BR-105. Присутствие считается по ежечасным кадрам.** «10 ч из 10» ≠ «работала 10 часов».
КП-BR-105-1: Given кадры раз в час → «часы в кадре» подписываются как присутствие, без формулировки «работала N часов».

### Блок B. Статусы работы (Ось 1)

**BR-201. Набор статусов и условия** (макет «Словарь → Ось 1»):

| Статус (чип) | Условие | Что делать |
|--------------|---------|-----------|
| `РАБОТА ИДЁТ` (ok) | техника в кадре, меняет положение, людей ≥ минимума | ничего |
| `ТОЛЬКО РЕСУРСЫ` (warn) | техника без движения, или нет ключевого класса, или людей меньше минимума | спросить причину простоя, **не обвинять** |
| `НИЧЕГО НЕ ОБНАРУЖЕНО` (bad) | кадры есть, ожидаемого нет | если работа закрыта в графике — запросить подтверждение до акта |
| `НЕДОСТАТОЧНО ДАННЫХ` (grey) | кадры < 60 % рабочих дней этапа | проверить камеру/объём вручную, **вердикт не выставляется** |
| `НЕ ПРОВЕРЯЕТСЯ` (grey) | нет в справочнике · нет видимых признаков · нет камеры · кадров не было | описать признаки / подключить камеру / принять |
| `НЕ НАЧАТА` (grey) | дата начала в будущем | ничего |
| `РЕШЕНО ВРУЧНУЮ` (blue) | человек закрыл как «объяснено»/«ложное» | ничего |

**BR-202 (ключевое). Цвет чипа наблюдения зависит ТОЛЬКО от наблюдения — не от отчётности и не от сроков.**
Источник: макет, «Лента расхождений»: «Цвет чипа никогда не зависит от отчётности и сроков».
КП-BR-202-1: Given работа подтверждена камерой и заявлено 100 % → чип `ok`, ось 2 — отдельной меткой.
КП-BR-202-2: Given работа закрыта на 100 %, камера ничего не видела → чип `bad` + **метка** «ЗАЯВЛЕНО 100 % · В КАДРЕ 0 ДН ИЗ 5» (не отдельный статус!).
КП-BR-202-3: Given просрочка срока, но работа идёт → чип `ok` + метка `+N ДНЯ К ПЛАНУ`.

**BR-203. «Недостаточно данных» — кадры меньше 60 % рабочих дней этапа.** Вердикт не выставляется.
КП-BR-203-1: Given кадры за 4 из 10 рабочих дней → `insufficient`, цвет серый.

**BR-204. «Не проверяется»** — если работа отсутствует в справочнике признаков, либо нет видимых признаков, либо нет камеры на зоне, либо кадров не было.

**BR-205. «Не начата»** — если дата начала плана в будущем.

**BR-206. «Решено вручную»** — после фиксации исхода «объяснено»/«ложное»; работа уходит из расхождений и счётчиков.

### Блок C. Подтверждение и пороги

**BR-301. Условие подтверждения:** `дней с уровнем 2 ≥ порог × прошедших рабочих дней этапа`.
Источник: макет «Работа подтверждена»; ТЗ R1.

**BR-302. Порог задаётся долей на вид работ** (не единый):
котлован **60 %**, армирование **80 %**, монолит **70 %**, бетонирование — **каждый день**.
КП-BR-302-1: Given армирование, подтверждено 3 из 5 дней (60 %) → **не** подтверждено (порог 80 %).
КП-BR-302-2: Given бетонирование, подтверждён не каждый день → **не** подтверждено.

**BR-303. Выходные и простои по акту исключаются из знаменателя.**

**BR-304. Порог и справочник меняются без правки кода** (настройка объекта, §4 «Справочник признаков»).
КП-BR-304-1: Given изменён порог в настройке → расчёт меняется без пересборки.

### Блок D. Три оси и цифры

**BR-401. Оси раздельны:** Ось 1 — чип наблюдения; Ось 2 — метка отчётности; Ось 3 — метка сроков.

**BR-402. Метка отчётности при разрыве ≥ 20 п.п.:**
- `ЗАЯВЛЕНО X % · В КАДРЕ N ДН ИЗ M` (красная) — заявлено **выше** наблюдения;
- та же метка синим — заявлено **ниже** наблюдения (отчётность отстаёт, **не претензия**).
КП-BR-402-1: Given заявлено 100 %, подтверждено 20 % → разрыв 80 п.п. → **красная** метка.
КП-BR-402-2: Given заявлено 55 %, подтверждено 90 % → разрыв −35 п.п. → **синяя** метка.

**BR-403. Единицы осей намеренно разные:** объём (%) и дни наблюдения не складываются; метка показывает **оба** числа.

**BR-404. Триада работы:**
```
план на сегодня = прошедшие рабочие дни этапа / все рабочие дни этапа
заявлено        = процент факта из графика
подтверждено    = дни с уровнем 2 / прошедшие рабочие дни этапа
```
Под триадой — «N из M дней».

**BR-405. Три полоски объекта** (план / заявлено / подтверждено), взвешены по длительности:
```
база = плановые рабочие дни всех ПРОВЕРЯЕМЫХ работ объекта
       (исключаются «не проверяется» и «недостаточно данных»)
план на сегодня = Σ прошедших рабочих дней работ / база
заявлено        = Σ (факт работы × её рабочие дни) / база
подтверждено    = Σ дней уровня 2 / база
                  (для «решено вручную» засчитываются все прошедшие дни)
```
КП-BR-405-1: Given объект без камер → «план» и «заявлено» считаются, «подтверждено» = «—».

### Блок E. Прогноз сроков

**BR-501. Прогноз — по наблюдаемому темпу.** Отставание = рабочих дней между плановым и прогнозным окончанием.

**BR-502. Прогноз объекта = по худшей работе.**

**BR-503. Если объём закрыт, но не подтверждён — прогноз не выставляется, и об этом написано.**
КП-BR-503-1: Given факт 100 %, подтверждение низкое → поле прогноза пусто + пояснение (не «в срок»).

### Блок F. Острота и «Требует настройки»

**BR-601. Внутренний балл остроты для сортировки:** закрыто без подтверждения **выше**, чем простой; простой **выше**, чем «недостаточно данных».

**BR-602. В продукте острота = функция** разрыва «заявлено − подтверждено», длительности простоя и суммы работы.

**BR-603. Блок «Требует настройки»** — не претензия к подрядчику (например, работа не в справочнике):
серая полоса, **нет остроты**, **нет** кнопки «Связаться», есть **«Описать признаки»**.

### Блок G. Жизненный цикл замечания

**BR-701. Состояния:** `новое → просмотрено → запрос отправлен → закрыто (исход)`.

**BR-702. «Не просмотрено N дней»** считается от появления замечания.

**BR-703. Панель «Связаться»** раскрывается в карточке: ответственный подрядчика (телефон, Telegram),
кому эскалировать через **двое суток** без ответа, и **готовый текст запроса** из фактов расхождения.
Три канала: звонок, Telegram, письмо — любой переводит карточку в «запрос отправлен».

**BR-704. Если ответственный не заполнен** — вместо панели жёлтое предупреждение и кнопка «Заполнить контакт» → настройка объекта.

**BR-705. Четыре исхода** (комментарий обязателен):

| Исход | Что меняется |
|-------|--------------|
| Подтвердилось · к удержанию по КС-2 | работа остаётся красной + метка «удержание по КС-2» |
| Объяснено подрядчиком | «решено вручную»: синяя полоса в Ганте, уходит из расхождений и счётчиков |
| Ложное срабатывание · в модель | то же + кадры в датасет на дообучение |
| Нет ответа · эскалация | остаётся красной + метка «эскалация» |

**BR-706. Закрывать может РП или технадзор.**

**BR-707. Закрытые по умолчанию скрыты**; возврат — фильтром «показать закрытые · N».

### Блок H. Камеры и дедупликация

**BR-801. Камера привязана к зоне.** Строка камер объекта: онлайн / был перерыв / молчит + время последнего кадра.

**BR-802. Камера молчит дольше суток → уведомление.**

**BR-803. Один объект не считается дважды при нескольких камерах.** Режимы: кластеризация по плану (гомография) либо присутствие (max по зоне).
КП-BR-803-1: Given 3 камеры видят один бульдозер в одной зоне → «1».

**BR-804. Кадры 08:00–17:00.** Ночные смены вне MVP.

**BR-805. Перекрытый обзор** — отдельного статуса нет: попадает в «ничего не обнаружено» с гипотезой «проверить обзор».

### Блок I. Простои по акту и режим недели

**BR-901. Режим работы площадки (5/6 + праздники) влияет на все проценты и календарь.** В демо — пятидневка.
КП-BR-901-1: Given суббота, режим 5 → день нерабочий, в знаменатель не входит.

**BR-902. Простой по акту** — день серый с пометкой «акт», **не считается ни за, ни против** подрядчика и **исключается из знаменателя**.
КП-BR-902-1: Given день помечен актом → работа с ним не получает «ничего не обнаружено».

### Блок J. Настройка

**BR-1001. Источник плана:** ссылка с автообновлением каждые **30 минут** либо разовый файл CSV/XLSX; в интерфейсе — перечень нужных колонок.

**BR-1002. Справочник признаков** (общий для объектов): для вида работ — классы техники и минимум, минимум людей, порог (доля рабочих дней).

**BR-1003. Тип зон:** `area` (полигоны) | `linear` (пикетаж).

**BR-1004. Ответственные:** контакт подрядчика на объекте + эскалация.

### Блок K. Источник факта («заявлено»)

**BR-1101. «Заявлено» хранится вместе с датой и автором.** Поля `report_date` и `author` —
необязательные. Под цифрой на экране: **«заявлено 80 % · Петров П.П. · на 1 сен»**.
КП-BR-1101-1: Given отчёт с датой и автором → под «заявлено» видны автор и дата.
КП-BR-1101-2: Given отчёт без даты/автора → показано только «заявлено N %», без подписи.

**BR-1102. Источник факта помечается.** `fact_source`: `plan_column` | `weekly_report` | `ks2` | `manual`.
КП-BR-1102-1: Given факт из недельного отчёта → на экране пометка «недельный отчёт».

**BR-1103. Два режима получения факта.**
- **Режим A (основной):** готовый процент из офиса подрядчика (+ дата, автор, источник).
- **Режим B (улучшение):** объёмы (плановый + фактический) → процент считаем сами.
Поля необязательные: старые графики без новых колонок читаются как раньше.
КП-BR-1103-1: Given старый график без `report_date`/`author`/`fact_source` → загрузка проходит, поля пустые.

> Уточнение: сейчас `report_date`/`author` описывают **последнее** значение «заявлено».
> Полная **история отчётов** по работе (30 % → 55 % → 80 %) — следующий шаг (отдельный слой факта).

## 4. Экраны (строго по макету)

### Экран 1 · Портфель

**Карточки объектов** (BR-405, BR-502, BR-201):
- цветная полоска сверху = худшее наблюдение (красная/жёлтая/зелёная/серая);
- бейдж «⚠ N замечаний» — **количество открытых карточек**, цвет по самому острому;
- стадия и число непроверяемых работ («нулевой цикл · 2 не пров.»);
- «+N дн к сроку» — прогноз по худшей работе (нет строки — сдвигов нет или объект не проверяется);
- три полоски с числами (план/заявлено/подтверждено).

**Строка сводки** — 5 чисел: открытых замечаний; объектов с замечаниями; замечаний, которые никто не открывал; задач по настройке; самое острое замечание (работа + объект). При выбранном объекте цифры остаются **портфельными**, фильтруется только лента.

**Сортировка и фильтры:** Лента/Таблица; по остроте; по объекту; по времени без реакции; по подрядчику; по разрыву «заявлено − подтверждено»; фильтры «никто не открывал · N», «только «ничего не обнаружено» · N», «показать закрытые · N».

**Лента расхождений** (одна карточка = одна работа): цветная полоса остроты; чип наблюдения; метки осей 2/3; путь «объект · зона · подрядчик»; текст вердикта 2–3 предложения; триада; «N из M дней»; кадр справа (камера, дата, время, «техника N · люди N»); нижняя строка кнопок.

**Блок «Требует настройки»** (BR-603).

**Панели «Связаться» (BR-703/704) и «Зафиксировать исход» (BR-705/706).**

**План-факт объекта** (Гант): шапка; строка статусов камер (BR-801); строка «прогноз сроков» (BR-501/502/503); по строке на работу — план, первая версия плана (если даты двигались), факт цветом наблюдения, прогноз; синяя вертикаль «сегодня»; выходные затемнены; окно «6 недель»/«весь объект»; клик по строке → разбор работы.

### Экран 2 · Разбор работы

- **Шапка:** работа, объект, зона, даты плана, подрядчик, заявленный %, чип наблюдения + метки (+ синий «решено вручную»).
- **Лестница подтверждения:** `01 · Ресурсы на месте` (детекция на кадре) → `02 · Работа идёт` (серия кадров за смену) → `03 · Объём растёт` (**в MVP всегда прочерк**) → `04 · Работа принята` (колонка факта). Расхождение = «04 да» при «01 нет»/«02 нет». Под лестницей — «Вывод».
- **Ожидалось и обнаружено:** класс техники, ожидалось/найдено/часов в кадре; строка «перемещение техники за смену»; строка «дней с активностью» (порог справочника vs факт).
- **Календарь и кадры смены:** слева календарь по месяцам, справа кадры выбранной смены (по умолчанию последняя; «К последней смене»). Легенда ячеек: день плана/работа шла/только ресурсы/ничего/кадров не было/выходной/простой по акту/будущий/сегодня/выбранный. Итог «подтверждено N из M прошедших рабочих дней плана», не зависит от месяца.
- **Возможные причины отклонения** — гипотезы, собранные из наблюдений и журнала плана; система **предлагает, не утверждает**.
- **История плана** — когда/кто менял даты и факт, с причиной; «не указана» красным; принцип: сверка с версией плана, действовавшей в день съёмки, **сдвиг дат задним числом красный статус не снимает**.
- **Работы без разбора:** завершённые — короткий вердикт + календарь; непроверяемые — причина и что сделать; не начатые — «наблюдений нет».

### Экран 3 · Камера

Кадр крупно с рамками: **зелёные — техника, синие — люди**, у каждой класс и уверенность модели. Скраббер по кадрам смены (закрашены деления, где ожидаемая техника найдена). Шапка: камера, зона, дата, число кадров, статус. Панели «На кадре» (классы/уверенности) и «Связь с графиком» (какая работа должна идти, что ожидалось, подтверждаются ли ступени 01 и 02).

### Экран 4 · Настройка

Блоки: Источник плана; Режим работы площадки (5/6 + праздники); Простои по акту; Уведомления; Тип зон; Камеры; Ответственные; Справочник признаков. (детали — BR-1001…BR-1004, BR-802)

## 8. Рассогласования (макет ↔ ТЗ ↔ код) — решить

1. **`false_completion` как отдельный статус vs принцип макета.** Макет: цвет чипа **никогда**
   не зависит от отчётности → «закрыто 100 % без подтверждения» это `nothing_detected` + **метка** `rep`.
   ТЗ v0.2 сделало `false_completion` статусом Оси 1 — это **нарушает** BR-202.
   **Предложение:** убрать `false_completion` из Оси 1, оставить как **признак/остроту** (высокую) при `nothing_detected` + заявлено 100 %.
2. **Портфель и три полоски** (BR-405) — в коде нет; нужен бэкенд-агрегат `/api/portfolio`.
3. **Версионирование плана** (`plan_v1`, `history[]`) — в коде нет; требуется для защиты от сдвига дат.
4. **Справочник признаков** пуст по объектам (в коде — общий JSON) — нужна привязка к работе/объекту.
5. **Уведомления** (камера молчит, без реакции 2 суток) — не реализованы.
6. **Слияние камер** — в макете помечено как ограничение; в коде `dedup.py` уже есть (лучше макета).
7. **Ночные смены, работы без видимых признаков** — вне MVP (совпадает).

## 9. Открытые вопросы

- Пороги по видам работ: утвердить (котлован 60 %, армирование 80 %, монолит 70 %, бетонирование ежедневно).
- Сколько часов без движения = простой по типам техники (см. вопросы Жасмин).
- Пятидневка/шестидневка — ответ эксперта меняет все проценты.
- Источник факта: график / недельный отчёт / месячная приёмка; **хранить дату отчёта**.
- LLM-импортёр графиков: ответственный и формат («правила + LLM»).
- Коды простоев по акту и кто подтверждает.
