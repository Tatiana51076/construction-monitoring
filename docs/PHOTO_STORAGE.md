# Хранилище фото — что нужно дашборду

> Понятное описание требований к фото-хранилищу и API.
> Для бэкенда (Георгий) и для презентации.

---

## 1. Зачем это (простыми словами)

Фото с камер — это **доказательство** работы системы. Дашборд показывает их в трёх местах:

1. **Лента расхождений** — один кадр на замечание («вот что видел, а вот что заявили»).
2. **Разбор работы** — серия кадров смены по дням (календарь + кадры).
3. **Экран камеры** — крупный кадр с рамками найденной техники.

Чтобы всё это работало, от хранилища нужно **две вещи**: **ссылка на каждое фото** и **список снимков с метаданными** (дата, объект, зона, камера). Всё остальное — удобство и фильтры.

---

## 2. Что нужно (по приоритету)

### Обязательное (без этого дашборд не покажет фото)

**1) Ссылка на фото.** В ответах `/upload` и `/results` добавить поле `image_url` — готовую ссылку на файл.

**2) Отдача файла.** `GET /uploads/{filename}` → сам файл с корректным `Content-Type: image/jpeg`.

**3) Список снимков.** `GET /photos` → список последних снимков с метаданными (для ленты и кадров смены).

### Желательное (фильтры для руководителя)

**4) Параметры фильтрации:** `object_id`, `zone_id`, `camera_id`, `work_id`, `date_from`, `date_to`, `limit`, `offset`.

**5) Сортировка** — по времени, свежие сверху (лента последних).

**6) Одна запись = один снимок** с детекциями и статусом работ.

---

## 3. Как это выглядит в API

**Список снимков:**
```
GET /photos?object_id=severny&date_from=2026-09-04&limit=20
```

**Ответ:**
```json
{
  "total": 2,
  "photos": [
    {
      "id": "1790086237",
      "file": "1790086237_test.jpg",
      "image_url": "/uploads/1790086237_test.jpg",
      "timestamp": "2026-09-04T08:15:00",
      "object_id": "severny",
      "zone_id": "zone-a",
      "camera_id": "cam-1",
      "detections": [
        { "class": "excavator", "confidence": 0.92, "bbox": [100, 200, 50, 80] }
      ],
      "works_status": [
        { "work_id": 1, "detected": true }
      ]
    }
  ]
}
```

**Ссылка на последнее фото** — добавить `image_url` в уже готовые ответы:
```
GET /results → { "last_upload": "...", "image_url": "/uploads/...", "detections": [...], "works_status": [...] }
POST /upload → { "status": "ok", "file": "...", "image_url": "/uploads/...", "detections": [...] }
```

---

## 4. Что хранить с каждым фото

Достаточно метаданных (в базе или рядом с файлом) — строгая структура папок не обязательна:

| Поле | Зачем |
|------|-------|
| `id` | уникальный идентификатор |
| `file` | имя файла |
| `image_url` | ссылка для отображения |
| `timestamp` | дата/время кадра (ISO) |
| `object_id` | объект — для фильтра |
| `zone_id` | зона — для фильтра |
| `camera_id` | камера — для фильтра |
| `detections` | рамки на фото (class, confidence, bbox) |
| `works_status` | какие работы обнаружены (work_id, detected) |

**Если хочется порядка в папках** (необязательно):
```
/uploads/{object_id}/{YYYY-MM-DD}/{camera_id}/{id}.jpg
```
Но для дашборда важен **`image_url` в ответе**, а не сами папки.

---

## 5. Если ничего делать не хочется

Минимум, который всё равно нужен:
- **`image_url`** в ответах `/upload` и `/results`;
- **отдача `/uploads/{file}`** по URL.

Тогда можно честно сказать: «фото доступны по URL», а ленту и фильтры (`GET /photos`) добавим вторым шагом.

---

## 6. Итог одной фразой

> Нам нужны **ссылка на каждое фото** и **список снимков с датой, объектом, зоной и камерой** — тогда дашборд покажет доказательства, ленту и кадры смены, а руководитель сможет фильтровать по объекту и дате.
