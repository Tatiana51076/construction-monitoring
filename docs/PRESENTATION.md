## Текст

**Объектив — интеллектуальный мониторинг строительной площадки.**

На стройке всегда есть две вещи — календарный график и камеры. Но сверяет их человек, вручную: смотрит кадры, звонит подрядчику, сопоставляет с таблицей. На это уходят часы, а срыв срока замечают поздно — когда он уже случился. «Объектив» делает эту сверку автоматически: нейросеть находит на снимках с камер технику и людей, система привязывает наблюдения к работам из графика и по каждому рабочему дню ставит уровень активности. Из этого складываются три вещи, которые видит руководитель: подтверждена ли работа наблюдением, расходится ли это с тем, что подрядчик заявил в графике, и насколько сдвигается срок. Каждое отклонение подтверждено кадрами.

Наш главный принцип — честность. Система не утверждает, что работа выполнена; она фиксирует только то, что видела: техника была или нет, двигалась или стояла. Всё, что не видно с камеры, честно помечается «не проверяется», а не закрашивается зелёным. Именно поэтому наши предупреждения обоснованные, адресные и справедливые.

Мы намеренно разделяем три независимые оси: наблюдение (что видела камера), отчётность (что заявил подрядчик) и сроки (сдвиг и прогноз). Цвет статуса зависит только от камеры и никогда — от отчёта или сроков. Благодаря этому работает главный сценарий защиты: подрядчик заявил 100 %, а камера техники не видела — система подсвечивает «ложное завершение».

Руководитель открывает портфель объектов — сверху самые проблемные, беспроблемные не отвлекают. Внутри объекта — план и факт по каждой работе, календарь «день / неделя / месяц», карта, риск и методология: откуда взялся вердикт и как он посчитан. Отдельно виден эффект переброски бригад: если отставание по одним работам компенсируется опережением по другим, срок объекта не сдвигается, а наверх всплывает слабое звено — например, поставщик арматуры.

Наша фишка — приложение прораба. Максимально простое: один тап — одно фото. Оно работает без интернета: фото копятся на телефоне и досылаются сами, когда появится связь. Дальше фото уходит в нейросеть, руководитель его оценивает — и формируется график фактически выполненных работ. Плюс соревнование бригад на объекте: это мотивация, а не надзиратель.

Технически: YOLO распознаёт 17 классов техники; дедупликация между камерами гарантирует, что один объект не посчитается дважды; бэкенд на FastAPI отдаёт понятный JSON API; интерфейс — React и TypeScript: дашборд руководителя и мобильное приложение прораба.

Почему мы выделяемся. Мы показываем честную картину, а не иллюзию. Подтверждаем выводы кадрами — меньше споров и обоснованнее удержания. Работаем там, где плохая связь. Не требуем идеальных фото. Мотивируем бригады, а не только контролируем. И готовы к внедрению: у нас уже есть рабочий API и единая форма данных.

Итог: срыв срока видят заранее, а не постфактум; ручной работы меньше, решения объективнее, расчёты справедливее. Статус портфеля руководитель понимает за тридцать секунд.

«Объектив» — это не камера, которая следит. Это система, которая видит стройку честно — и помогает не сорвать срок, а не искать виноватого. Ставьте камеры. Дайте нам график. Остальное сделаем мы.

## Короткая версия для устной защиты (30 секунд)

На стройке есть график и камеры, а сверяет их человек — вручную. «Объектив» делает это сам: нейросеть находит технику на кадрах, система привязывает её к работам и показывает, что реально идёт, где подрядчик заявил лишнее и насколько сдвинется срок — с доказательством кадрами. Наш принцип — честность: мы показываем только то, что видели, а непроверяемое честно помечаем. Плюс приложение прораба: один тап — фото, работает без связи, и соревнование бригад. Камеры есть у многих — мы даём то, что превращает их в управление стройкой.

## Документация нашей части

Мы делали бизнес-аналитику и приложение:
1. Каноническая форма данных плана/факта — единый язык для плана, отчёта и кода.
2. Правила сверки R1–R8 и статусы (наблюдение / ресурсы / ничего / недостаточно данных / ложное завершение).
3. Три оси (наблюдение / отчётность / сроки) и таблица «план-факт».
4. Бизнес-логика приложения прораба: офлайн-ферст, ≤2 тапа, соревнование бригад, факт работ, схема состояний фото, модель данных, экраны.
5. Логика экранов руководителя: портфель по проблемности, выбор проектов, календарь «день/неделя/месяц», карта, риск, методология.
6. Интеграция с API бэкенда: `/health`, `/upload`, `/works`, `/results`.

Наши документы в репозитории:
```
TZ.md                      — ТЗ v0.2 (синхронизировано с макетом «Объектив 0.4»)
docs/REQUIREMENTS.md       — выжимка требований и правила сверки
docs/DEV_REQUIREMENTS.md   — требования для разработчика: бизнес-правила BR + критерии приёмки
docs/FOREMAN_APP.md        — бизнес-логика приложения прораба
docs/FOREMAN_APP.html      — та же логика красиво, со схемами
docs/DISCUSSION.md         — повестка обсуждения бизнес-аналитики
docs/mockup-foreman-app.html — макет 3 экранов приложения прораба
docs/PHOTO_STORAGE.md      — требования к хранилищу фото (для бэкенда и презентации)
docs/diagrams/*.puml|*.png — схемы (акторы, модель данных, жизненный цикл фото)
docs/objectiv-app/         — собранное приложение «Объектив» (для просмотра)
```

API-контракт (по ТЗ бэкенда):
```
GET  /health   → { "status": "ok" }
POST /upload   → { "status":"ok", "file":"...", "detections":[
                    { "class":"excavator", "confidence":0.92, "bbox":[x,y,w,h] } ] }
GET  /works    → { "works":[ { "id":1, "name":"Земляные работы", "status":"in_progress" } ] }
GET  /results  → { "last_upload":"...", "detections":[...],
                    "works_status":[ { "work_id":1, "detected":true } ] }
```
bbox: `[x_центр, y_центр, w, h]` в пикселях (центр бокса + размеры).

Ключевые принципы: система фиксирует, а не утверждает; «не проверяется» — честный статус; оси не смешиваются; простои по акту исключаются; претензии — только с доказательством; офлайн-ферст и минимум действий.
