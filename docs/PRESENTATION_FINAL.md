## Слайд 1 · Титул

**«Объектив» — интеллектуальный мониторинг строительной площадки**

Камеры → нейросеть → сверка с календарным графиком → честный вердикт с доказательством кадром.

---

## Слайд 2 · Проблема и актуальность

На стройке есть два инструмента — календарный график и камеры. Но сверяет их человек **вручную**: визуальный просмотр камер, звонки подрядчику, субъективная оценка.

- Трудоёмко и медленно — срыв срока замечают, когда он уже случился.
- Подвержено ошибкам — «на глаз».
- **Ключевое: отчёту подрядчика нельзя верить без доказательства.** «Заявлено 100 %» не значит «сделано».

Камеры на площадках **уже установлены** — значит, автоматизацию можно внедрить без дорогого железа.

---

## Слайд 3 · Решение (концепция)

«Объектив» анализирует снимки с камер, распознаёт строительную технику, сопоставляет её с этапами календарного плана и **выявляет отклонения** с объяснением и доказательством.

**Главный принцип — честность:** система фиксирует только то, что видела, а не утверждает, что работа выполнена. Непроверяемое честно помечается «не проверяется».

Отвечаем на вопрос: **«идёт ли стройка по плану — и можно ли верить отчёту подрядчика»**.

## Слайд 4 · Архитектура (компоненты и взаимодействие)

[сюда — диаграмма C4]

Компоненты:
- **Камеры на площадке** → кадры.
- **CV-сервис (YOLO)** → обнаружение 17 классов техники (класс, уверенность, bbox).
- **Бэкенд (FastAPI)** → дедупликация между камерами, сверка с планом (правила R1–R8), статусы.
- **БД PostgreSQL** + хранилище фото.
- **Дашборд (React)** — руководитель · **приложение прораба** — факт с площадки.

Взаимодействие: `фото → детекция → сопоставление с планом → вердикт → дашборд и приложение прораба`.

## Слайд 5 · Обоснование технологий и ML-моделей

| Технология | Почему выбрана |
|---|---|
| **YOLO** | лучший баланс точность/скорость; готовые веса + дообучение; работает без GPU |
| **FastAPI** | быстрый JSON API, авто-документация `/docs`, лёгкая интеграция с CV |
| **React + TypeScript** | интерактивный дашборд, быстрая оценка статуса |
| **PostgreSQL (SQLite для демо)** | хранение этапов, наблюдений, отклонений |
| **Docker** | воспроизводимый запуск (Dockerfile + docker-compose) |

Ключевое ограничение: прототип работает на **стандартном ноутбуке**, без GPU.

## Слайд 6 · Схема: как снимки связываются с этапами графика

[сюда — sequence/pipeline диаграмма]

```
Снимок → Детекция (класс, уверенность, bbox)
       → Дедупликация между камерами (один объект = один)
       → Уровень дня по работе (работа идёт / только ресурсы / ничего / нет кадров)
       → Методика «этап → техника»
       → Сверка с планом и отчётом подрядчика
       → Отклонение с зоной и снимком
```

**Методика (правила «этап → техника»):**
- «Котлован» → экскаватор + самосвалы.
- «Бетонирование» → миксер, кран-манипулятор, автокран.
- «Армирование» → ковшовый погрузчик + самосвал.

## Слайд 7 · Демонстрация прототипа

Сквозной сценарий (показать на живом интерфейсе или скриншотами):

1. **Кадр с камеры** → распознана техника (рамки, класс, уверенность).
2. **Сопоставление с этапом** → статус работы.
3. **Отклонение** → предупреждение с зоной и снимком.

**Пример:** этап «Устройство котлована» — виден экскаватор, но нет самосвалов → предупреждение «возможное снижение темпа работ, зона A» + снимок-доказательство.

## Слайд 8 · Выявление отклонений

- **Отсутствие техники** — нет техники, необходимой по плану.
- **Лишняя техника** — техника не соответствует текущему этапу.
- **Ложное завершение** — подрядчик заявил 100 %, камера технику не видела.
- **Простой по акту** — исключается из расчёта (погода, технология).

Каждое замечание: **зона + снимок + формула** — содержательно и объяснимо.

## Слайд 9 · Масштабирование и развитие

**Фаза 0 (сейчас):** демо — камера → нейросеть → сверка → вердикт.
**Фаза 1 (4–6 нед):** пилот на 1 объекте — реальные камеры, график заказчика, акты простоя.
**Фаза 2 (2–3 мес):** продукт — портфель объектов, импорт Excel/КС-2, роли, отчёты.
**Фаза 3 (6–12 мес):** платформа — дообучение (арматура/двери/дефекты), прогноз сроков, 1С/BIM, API.

**Бизнес-модель:** подписка за объект (SaaS), старт с бесплатного пилота.

## Слайд 10 · Рекомендации по установке камер

- **Одна камера → одна зона**; при перекрытии — назначить главную камеру.
- Обзор ключевых зон: котлован, пути вывоза, склад, монтаж.
- Частота: **1 кадр/час** в смену (достаточно для уровней дня и движения).
- Ночь/плохая погода — ИК-подсветка; иначе смена не оценивается.
- Высота и ракурс — для различимости классов техники.
- Контроль «камера молчит дольше суток» → уведомление.
- Для точного счёта — калибровка (гомография) и привязка камеры к плану.

## Слайд 11 · Итог

Мы не «считаем, сколько построено». Мы отвечаем на вопрос **«идёт ли стройка по плану и можно ли верить отчёту»** — с доказательством кадрами.

Камеры есть у многих, график — у всех. Никто не связывает их в **честный аудит с доказательством** — мы делаем это первыми.

**Реализуемо:** без дорогого железа, без BIM, на существующих камерах, с приложением, которое работает даже без связи.
