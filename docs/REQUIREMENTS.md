# Требования и правила сверки (выжимка для бэкенда и документации)

> **Источник истины:** `TZ.md` (v0.2 — макет «Объектив 0.4», лежит в корне проекта).
> Этот файл — сжатая выжимка: что система делает, данные на входе, как считаются статусы.
> Для бэка: §6–§9 — ядро, §15 — что ещё не реализовано в коде.
> **Для разработки (бэк и фронт): `docs/DEV_REQUIREMENTS.md` — бизнес-правила BR с критериями приёмки.**

## 0. Терминология (ТЗ ↔ макет ↔ код)

| ТЗ | Макет | Код | Значение |
|----|-------|-----|----------|
| Этап / вид работ | Работа | `Work` | Строка календарного плана |
| Справочник признаков | — | `rules` / `required_equipment` | Какая техника/люди нужны работе |
| Зона / участок | Зона | `zone` | Территориальная привязка |
| Обнаружение техники | Наблюдение | `Observation`, `Detection` | Что видно на кадре |
| Отклонение | Замечание | `Deviation` | Наблюдение ≠ план/отчёт |
| Отчёт подрядчика | Заявлено | `fact_percent` | Что подрядчик проставил |
| Подтверждение | Подтверждено | `days level 2 / days` | Доля дней, где камера видела работу |
| Событие | Кадр / смена | `snapshot`, `shift` | Единица съёмки |
| Ответственный | Контакт подрядчика | `contacts` | Кому адресуется замечание |

Три независимые оси: **Ось 1 — наблюдение, Ось 2 — отчётность, Ось 3 — сроки**.

## 1. Что делает система

По снимкам с камер стройплощадки определяет, **какие работы фактически идут**, сверяет
с календарным планом и отчётностью подрядчика, выявляет **отклонения** с доказательством
(кадры) и оценкой **риска срыва сроков**.

**Главный принцип:** система не утверждает, что работа выполнена. Фиксирует только то,
что **видела** (техника была/нет, двигалась/стояла). Непроверяемое честно помечается
«не проверяется», а не «выполнено».

## 2. Входные данные

1. **Снимки:** `{path, camera_id, zone, timestamp, shift}`.
2. **Камеры:** `{id, name, zone, is_primary_for_zone, status, last_frame_at, homography?}`.
3. **Работы (план/факт):** каноническая форма, см. §3.
4. **Отчёт подрядчика:** та же форма + `report_date, author`.
5. **Справочник признаков:** для работы — классы техники, минимум людей, порог подтверждения.
6. **Простои по акту:** `[{date, reason}]` (погода, технология, внешние причины).
7. **Контакты:** ответственный подрядчика на объекте + эскалация.

**8 классов техники (обязательный перечень ТЗ):**
`dump_truck`, `excavator`, `roller`, `manipulator_crane`, `concrete_mixer`, `bulldozer`,
`truck`, `truck_crane`.
**Люди** — вспомогательный признак (претензия на нём одном не строится).

## 3. Каноническая форма работы

| Поле | Обяз. | Описание |
|------|:---:|----------|
| `id` | да | идентификатор |
| `object_id` | да | объект (корпус/секция/площадка) |
| `name` | да | вид работ |
| `zone` | да | зона/участок (захватка, этаж, ось) |
| `contractor` | да | подрядчик |
| `plan_start`, `plan_end` | да | даты плана |
| `required_equipment` | да | нужные классы техники |
| `min_counts` | да | мин. кол-во техники |
| `confirm_threshold` | да | порог подтверждения (доля, напр. 0.6) |
| `fact_percent` | да | факт, % |
| `zone_type` | да | `area` / `linear` |
| `fact_start`, `fact_end` | нет | факт даты |
| `report_date` | нет | на какую дату заявлено «выполнено» |
| `author` | нет | кто проставил процент |
| `fact_source` | нет | откуда факт: `plan_column` / `weekly_report` / `ks2` / `manual` |
| `responsible` | нет | ответственный (человек) → адресность замечаний |
| `volume`, `unit` | нет | объём и ед. изм. |
| `predecessors` | нет | зависимости → объяснение причины (root cause) |
| `source`, `version` | нет | источник/версия → трассируемость и аудит |

**Импорт любого графика** приводится к этой форме (правила + LLM), чтобы РП не переделывал файл руками.

## 4. Пайплайн

```
Снимки → Детекция (техника+люди) → Дедупликация между камерами
      → Уровень дня (0/1/2/null) по работе (зона+даты)
      → Подтверждение (доля дней уровня 2 ≥ порог работы)
      → Сверка трёх осей (наблюдение / отчётность / сроки)
      → Замечания + острота + прогноз срока
      → Дашборд
```

## 5. Уровень дня (базовая единица)

```
2 · работа идёт     требуемая техника в кадре, меняет положение, людей ≥ минимума
1 · только ресурсы  техника есть, но без движения, ИЛИ нет ключевого класса, ИЛИ людей мало
0 · ничего          кадры есть, требуемой техники и бригады нет
null · кадров нет   камера молчала (в расчёт не берётся)
```

## 6. Статусы работы (Ось 1 — наблюдение)

| Статус | Условие | Действие |
|--------|---------|----------|
| `in_progress` | доля дней уровня 2 ≥ `confirm_threshold` работы | ничего |
| `resources_only` | техника стоит смену / нет ключевого класса / мало людей | спросить причину простоя |
| `nothing_detected` | кадры есть, ожидаемого нет | если работа закрыта — запросить подтверждение до акта |
| `insufficient` | кадры < 60% рабочих дней этапа | проверить камеру/объём вручную, вердикта нет |
| `not_checked` | нет в справочнике / нет признаков / нет камеры / нет кадров | описать признаки/камеру |
| `not_started` | план в будущем | — |
| `manual_resolved` | человек закрыл как «объяснено»/«ложное» | — |

## 7. Правила сверки (R1–R8)

- **R1 «Работа идёт»:** доля дней уровня 2 ≥ `confirm_threshold` работы. Порог **на работу**:
  котлован 60%, армирование 80%, монолит 70%, бетонирование — ежедневно.
  Выходные и дни простоя по акту из знаменателя **исключаются**.
- **R2 «Только ресурсы»:** техника в кадре, но `moved=false` за смену, и/или нет ключевого
  класса, и/или людей < минимума.
- **R3 «Ничего не обнаружено»:** кадры есть, требуемой техники/бригады нет
  `missing_days=2` дней подряд.
- **R4 «Недостаточно данных»:** покрытие < 60% рабочих дней этапа → вердикт не выставляется.
- **R5 «Лишняя техника» (`unexpected_equipment`)** ⭐: на работе видна техника вне её
  справочника → замечание (низкая/средняя острота).
- **R6 «Ложное завершение» (`false_completion`)** ⭐: `fact_percent = 100`, покрытие ≥ 60%,
  доля дней уровня 2 < 40% → high. Формулировка: «выполнение **не подтверждено**
  видеонаблюдением».
- **R7 «Сроки»:** начало сдвинулось относительно плана; прогноз окончания по темпу;
  «+N рабочих дней к плану».
- **R8 «Отставание отчётности» (не претензия):** наблюдение выше заявленного на ≥20 п.п.

## 8. Multi-camera dedup (обязательно)

Один объект не должен считаться за несколько:
1. **При калибровке:** детекции одного типа в пределах `dedup_distance` и окна
   `dedup_window_min` → один объект (гомография на план).
2. **Без калибровки (fallback):** по (зона, тип) берётся **max по камерам**, а не сумма.
3. За камерами закреплены зоны; при перекрытии — **главная камера зоны**
   (`is_primary_for_zone`).

Реализация: `backend/app/cv/dedup.py`.

## 9. Три оси в карточке замечания

```
план на сегодня   = прошедшие рабочие дни этапа / все рабочие дни этапа
заявлено          = fact_percent из графика
подтверждено      = дни уровня 2 / прошедшие рабочие дни этапа
разрыв            = заявлено − подтверждено; метка при |разрыв| ≥ 20 п.п.
```
Единицы намеренно разные: объём (%) и дни наблюдения не складываются в одну шкалу.

## 10. Острота и прогноз

- **Острота** (сортировка ленты): закрыто без подтверждения > простой > «недостаточно данных».
- **Прогноз срока:** по наблюдаемому темпу; если объём закрыт, но не подтверждён — не выставляется.

## 11. Жизненный цикл замечания

`новое → просмотрено → запрос отправлен → закрыто (исход)`

| Исход | Смысл | Что меняется |
|-------|-------|--------------|
| Подтвердилось · удержание по КС-2 | подрядчик не доказал объём | остаётся красным + метка удержания |
| Объяснено подрядчиком | фотоотчёт, работы вне обзора | синий «решено вручную», уходит из расхождений |
| Ложное срабатывание · в модель | ошибка детектора | кадры в датасет, «решено вручную» |
| Нет ответа · эскалация | 2 суток молчания | остаётся красным + метка эскалации |

## 12. Простой без вины подрядчика

Причины (коды): `weather`, `access_not_granted`, `design_documentation`,
`customer_materials`, `adjacent_works`, `technology_break`, `external_restriction`,
`force_majeure`, `design_error`.
При наличии документа — день **серый, исключается из расчёта**; без документа —
«требует подтверждения». Формат: `downtime[] : {date, reason, document?}`.

## 13. Пороги (конфиг, меняются без правки кода)

```
confirm_threshold (на работу) = 0.6 | 0.7 | 0.8 | 1.0
coverage_min = 0.6
missing_days = 2
idle_move = false за смену → уровень 1
dedup_distance = 3.0
dedup_window_min = 5
week_mode = 5 | 6 + праздники
```

## 14. Нефункциональные требования

- Без GPU — допустимо; GPU — приветствуется.
- Отклик API < 2 с (без времени детекции).
- Docker: `Dockerfile` + `docker-compose.yml`.
- Код модульный и документированный; БД PostgreSQL (SQLite для демо).

## 15. Состояние кода vs ТЗ v0.2

**Реализовано:**
- `Work` (каноническая форма), `DayLevel`, `Downtime`, `WorkStatus` — `schemas.py`.
- Уровни дня 0/1/2/null, статусы, три оси, прогноз — `matching/daylevel.py`.
- Правила R1–R8: `false_completion`, `schedule_delay`, `idle` — `matching/engine.py`;
  пороги — `app/config.py`.
- Канонический CSV-график с синонимами колонок — `matching/schedule.py`.
- Дедуп между камерами: 2 режима (кластеризация по плану / присутствие) — `cv/dedup.py`.
- Эндпоинт `POST /api/work-status` — `routes/status.py`.
- Тесты — `tests/test_daylevel.py`, `tests/run_all.py` (16 тестов, все зелёные).

**Осталось (следующий шаг):**
- Накопление `days` из кадров смены (сейчас уровень дня считается по переданным данным).
- Жизненный цикл замечания (`новое → … → закрыто`) и удержание по КС-2.
- Версионирование плана (`source/version`, `plan_v1`, журнал изменений) — защита от
  сдвига дат задним числом.
- `predecessors` → объяснение причины (root cause).
- `risk_score`: веса `false_completion=40, schedule_delay=25, missing_equipment=30,
  undercapacity=15, idle=10, unexpected_equipment=5`; штраф `min(days_overdue,10)*5`,
  итог 0..100.

## 16. Критерии приёмки

- Все обязательные функции ТЗ работают сквозняком на демо-данных.
- РП за ≤30 сек понимает статус портфеля.
- Каждое замечание объяснено и подтверждено кадром.
- Multi-camera: один объект = один (не N камер).
- Пороги и справочник меняются без правки кода.
